# Spotter Freight Rate Prediction — Machine Learning Engineer Assessment

## Overview

This repository contains an end-to-end solution for the Spotter Machine Learning Engineer freight-rate assessment.

The pipeline:

1. Loads the labeled development data.
2. Cleans corrupted/missing shipment fields without using future validation labels.
3. Engineers temporal, route, load, interaction, and geographic features.
4. Uses chronological backtesting to reflect the November–December future prediction setting.
5. Models normalized `posted_rate / distance` with robust L1 LightGBM objectives.
6. Blends a market-aware model with a market-agnostic model for robustness.
7. Retrains on all January–October labeled data.
8. Produces the required 12,000-row validation prediction file.
9. Produces the 31-row December scenario file.
10. Runs the supplied validation contract and generates `scorer_results/candidate_december.png`.

## Data

Expected files under `data/`:

- `train_test.csv`
- `validation.csv`
- `validation_predictions_template.csv`
- `december_chart_inputs.csv`

The supplied development data contains 48,000 labeled loads from January through October 2025. The final validation set contains 12,000 loads from November and December 2025.

## Modeling approach

### Target formulation

The primary target is normalized freight cost:

`rate_per_mile = posted_rate / distance`

The model predicts log-transformed rate-per-mile and converts it back to dollars:

`predicted_rate = exp(predicted_log_rate_per_mile) * distance`

This separates the strong distance effect from lane/equipment/temporal effects and makes the model less sensitive to large-dollar scale differences.

### Data quality

The development data contains:

- 292 negative weight values.
- 300 missing weights.
- 374 missing market-index values.
- 772 observations with extreme rate-per-mile values outside the 0.30–3.00 range.

Negative weights are treated as sign corruption and converted to absolute values. Missing numeric fields are imputed using statistics fit from the labeled development data. Extreme rate-per-mile values are not deleted; the log target and L1 objective provide robustness while preserving every training observation.

### Features

The model uses:

- pickup and delivery cities
- equipment
- route and route-equipment identifiers
- shipment distance
- cleaned weight
- weight-per-mile
- pickup/delivery coordinates
- haversine distance
- coordinate deltas and direction
- calendar features
- seasonal sine/cosine features
- market index and quote signal
- market/quote interaction features

For the December chart, market index and quote signal are intentionally excluded because those fields do not exist in the provided chart-input schema. City coordinates are recovered from robust medians learned from the development data.

### Validation

Random train/test splitting was deliberately avoided because the final 12,000 loads occur after the labeled period.

Primary chronological holdout:

- Train: January–August 2025
- Holdout: September–October 2025
- MAE: $104.46
- RMSE: $633.92
- MAPE: 4.42%
- R²: 0.827

Recent-period stress test:

- Train: January–September 2025
- Holdout: October 2025
- MAE: $96.68
- RMSE: $645.51
- MAPE: 4.48%
- R²: 0.822

These are internal historical holdout metrics, not the hidden Spotter score.

### Final ensemble

The final validation prediction is:

- 70% market-aware LightGBM
- 30% market-agnostic LightGBM

Both models use a robust L1 objective, shallow trees, log rate-per-mile target, and chronological model selection.

The market-agnostic component improves stability when market variables are missing or their future behavior is uncertain.

## Reproducibility

Random seeds are fixed in the LightGBM models. All preprocessing statistics are learned from the labeled development dataset. The validation target is never used during final prediction generation.

## Limitations

The true `posted_rate` for the 12,000 validation loads is hidden by the assessment. Consequently, the final Spotter score cannot be calculated locally. Internal metrics are used only for model selection and sanity checking.
